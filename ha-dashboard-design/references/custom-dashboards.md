# Custom dashboards and original themes

> *Generated by [aurora@aurora-smart-home (home-assistant skill)](https://github.com/tonylofgren/aurora-smart-home)*

Checked against upstream documentation on 2026-10-22. A custom dashboard can use HA as
its data and control layer while having its own composition, typography, navigation and
visual identity. Do not reduce "make it my own" to recoloring standard tiles.

## Start with the design

Use the user's references, colors and intended device. Establish the primary tasks and
screen dimensions, whether custom cards are acceptable, and whether HA navigation should
remain visible. If the user has no aesthetic preference, propose a coherent direction and
continue: for example editorial typography with a warm paper background, wide spacing,
large climate readings and a small set of prominent controls.

Define reusable tokens for background, surface, text, muted text, accent, warning, spacing,
radius and typography. Use local/system fonts unless a bundled font is needed. Separate
layout from entity bindings so the same design can be reused in another home.

## Pick the implementation

| Need | Implementation | Tradeoff |
|---|---|---|
| Custom palette and font | HA theme | Small maintenance cost; native card structure remains |
| Completely different view composition | Panel + layout-card + button-card | Responsive grid and custom surfaces; two frontend dependencies |
| A single unique visualization/control | Custom web-component card | Own rendering and interaction code, still inside Lovelace |
| An entire bespoke application surface | Custom panel | More routing, accessibility and maintenance work |
| Separate site/app | HA authenticated API client | Explicitly separate project with authentication and deployment requirements |

Do not embed long-lived access tokens in dashboard YAML, JavaScript or public `/local/`
assets. A custom card receives `hass`; reuse that authenticated context. Render entity
text safely rather than injecting arbitrary state strings as HTML. A standalone frontend
needs an actual authentication flow, not a token pasted into a static HTML file.

Native [sections](https://www.home-assistant.io/dashboards/sections/) are suitable for
responsive visual editing. A [panel](https://www.home-assistant.io/dashboards/panel/)
contains one full-width root card. The editorial starter uses that root for a grid.
[layout-card](https://github.com/thomasloven/lovelace-layout-card) supplies grid placement
and `mediaquery`; put the narrowest matching rule first.

## Theme, card styles and resources are different

1. Merge `frontend: themes: !include_dir_merge_named themes/` into the existing HA config.
2. Store the theme mapping under `themes/`, reload themes, and choose its name on the view.
3. Install custom cards through HACS or manually, registering each JavaScript module once.
4. Put button-card styles under `styles:` and card-mod under each target card's `card_mod:`.
   Do not paste CSS mappings into the dashboard resource list.

[Theme variables](https://www.home-assistant.io/integrations/frontend/) change frontend
appearance. Private CSS variables and shadow-DOM selectors can change between versions;
keep overrides local. [card-mod](https://github.com/thomasloven/lovelace-card-mod) supports
card styling and its own theme conventions; it is optional, not a prerequisite for every design.

For custom components, follow the [custom-card API](https://contributors.home-assistant.io/frontend/custom-ui/card/):
validate configuration in `setConfig`, respond to `hass` updates, handle missing entities,
and implement sizing for the selected layout. A dashboard theme alone does not replace
HA's navigation shell. Use a custom panel or an explicitly chosen kiosk extension when
that shell is part of the request, keeping an administrative escape path.

## Starter and delivery

[Custom Editorial](../assets/custom-editorial/README.md) is a complete dashboard plus theme.
It deliberately has a magazine-like header, large measurements and asymmetric desktop
placement; on a phone it becomes a single ordered column. It uses button-card and
layout-card, with no mandatory Mushroom or card-mod dependency.

For a user project, deliver `dashboards/<name>.yaml`, the required `themes/<name>.yaml`
and root README. Include both Raw Configuration Editor and named YAML-dashboard install
paths. List dependencies and real entity bindings. Keep placeholder IDs only in reusable
templates, never present them as discovered live entities.

## Verification

- Parse YAML; verify template names, resources, theme name and panel/sections structure.
- Inspect at 360 px, tablet and desktop widths, with long translated labels and 200% zoom.
- Check missing, `unknown`, `unavailable`, on/off and loading states. Missing readings must
  not become zero or falsely indicate that a room is safe.
- Keep controls at least 44 px high, provide text as well as color, and retain keyboard
  focus. Test real tap/hold actions in HA; require confirmation for consequential operations.
- Check light/dark contrast and reduced-motion behavior if adding animation.
- Report whether it was rendered in live HA. YAML parsing or a static preview does not
  prove custom cards loaded or a service call reached a device.

Presets are useful starting points. They never constrain a user's own theme or layout.
